# stroyka

## Продукт

Веб-сервис, через который студия дизайна интерьера показывает частному
заказчику ход работы над его проектом. Квартиры и частные дома, срок 2–4 месяца.

Заказчик открывает ссылку на страницу своего проекта и видит этапы, материалы
с них — планировки, коллажи, визуализации, листы рабочей документации — и
короткие записи о сделанном. Менеджер студии раз в 1–3 дня выкладывает файлы,
отмечает этап и пишет одну строку для заказчика.

Учебный проект: цель — освоить бэкенд и получить кейс в портфолио.

## MVP

Две роли: менеджер и заказчик. Один сквозной сценарий — публикация материалов
этапа.

Менеджер загружает изображения, выбирает этап, пишет строку и публикует.
Заказчик открывает ссылку без пароля и видит текущий этап, индикатор прогресса
по 7 этапам и ленту опубликованных записей с изображениями.

Сценарий односторонний: студия публикует, заказчик смотрит. Согласование
заказчиком («принял» / «переделать») в MVP не входит — см. «После MVP».
Это осознанный размен ради того, чтобы довезти сервис до живого домена.

Эндпоинты: `GET /objects/:id`, `GET /objects/:id/events`, `POST /files`,
`POST /events`, `PATCH /stages/:id`.

Создание компании, сотрудника, проекта и этапов — через сид, руками.
Ссылка заказчику отправляется вручную.

Итог: сервис развёрнут на своём домене под HTTPS, с демо-проектом и живыми
материалами, проходится за 30 секунд с телефона — менеджер публикует запись,
заказчик видит её в ленте.

## Стек

Утверждён, альтернативы не предлагать.

Бэкенд: NestJS + TypeScript, Postgres, Drizzle ORM, BullMQ + Redis, MinIO,
sharp, Docker.
Фронт: Next.js + Tailwind.
Тесты и CI: Jest (unit + e2e), GitHub Actions на пуш — линт и тесты.
Деплой: VPS в РФ, Caddy. В проде вместо MinIO — S3-совместимое хранилище
(Yandex Object Storage), API тот же.
Среда разработки: Windows, PowerShell, VS Code.

В MVP принимаются только растровые изображения (JPG, PNG). PDF рабочей
документации требует отдельного рендерера в контейнере — в `IDEAS.md`.
`exifr` из стека убран: у визуализации из рендера нет ни даты съёмки,
ни координат, зависимость перестала решать задачу.

## Модель данных

Таблицы: `companies`, `objects`, `stages`, `files`, `events`, `event_files`.

`objects` — проект (квартира или дом), а не стройплощадка. Имя таблицы
намеренно нейтральное.

`events` — центральная таблица, лента заказчика строится из неё. Сейчас один
тип события: `deliverable` — выложены материалы по этапу. Позже добавятся
другие типы — так расширяется продукт, схема при этом не переделывается.

Принятые решения:

- `company_id` есть в каждой таблице, кроме `event_files`: к связке не
  обращаются напрямую, только через `events`, где фильтр уже стоит
- все timestamp — `timestamptz`: сервер живёт в UTC, заказчик читает
  время в своём поясе
- `published_at` nullable timestamp вместо булева `is_published`
- индекс `(object_id, created_at desc)` на `events`
- `order_index` у этапов (`order` — зарезервированное слово)
- хранить оригиналы файлов, не только превью
- у события есть автор с ролью (`manager` / `designer`), а не просто ссылка
  на менеджера
- `type` у события — строка, новые значения добавляются без изменения схемы
- заказчик входит по ссылке с `invite_token` без пароля, сотрудник — по логину
  и паролю
- лента отдаёт события, не зная их типов: фильтр только по `object_id`
  и `published_at`, никаких `if (type === ...)` в запросе

## Этапы проекта

Семь этапов, `order_index` 1–7:

1. Замер и техзадание
2. Планировочное решение
3. Концепция
4. 3D-визуализации
5. Рабочая документация
6. Ведомости и спецификации
7. Авторский надзор

Список сверяется с составом работ, опубликованным на сайтах реальных студий.
Если формулировки разойдутся — это правка сида, не миграция.

## Вне скоупа

Отказывать, если просят добавить. Предлагать записать в `IDEAS.md`.

Смета, деньги, допсоглашения, договоры, чат, вопросы заказчика, уведомления,
чек-листы, отчёты, ИИ, боты в мессенджерах, биллинг, регистрация компаний,
роли сверх двух.

Отдельно для этой предметной области — тянет сильнее всего, отказывать так же:
подбор материалов и мебели, мудборды с выбором вариантов, ведомости закупок
со ссылками на магазины, 3D-туры и панорамы, интеграции с CAD и BIM,
онлайн-согласование правок с комментариями поверх изображения.

Правило распространяется и на инфраструктуру: сервис появляется в
`docker-compose.yml`, только когда есть задача, которая без него не решается.

## После MVP

Черновик, не план. Порядок и состав уточняются по ходу: что-то отпадёт,
что-то появится. Ничего отсюда не берётся в работу, пока MVP не закрыт
и пункт не перенесён в `TASKS.md`.

Правило расширения: новая функция — это новый тип события в той же таблице
`events` и новый блок на тех же экранах. Если для неё приходится переделывать
`events`, `files` или схему проекта — значит она спроектирована неправильно,
а не схема.

| Что | Тип события | Уточнить перед началом |
|---|---|---|
| Согласование этапа заказчиком: «принял» / «на доработку» | `stage_approved`, `revision_requested` | сколько кругов правок и блокирует ли отказ переход к следующему этапу |
| Дизайнер: ссылка со списком своих проектов, та же форма загрузки | `deliverable` | нужен ли выбор проекта или хватит одного активного |
| PDF рабочей документации: превью первой страницы, скачивание | `deliverable` | чем рендерить и класть ли рендер в очередь BullMQ |
| Смета проекта в позициях с версиями, экран «Деньги» | `estimate_updated` | откуда берётся смета: импорт Excel или ввод руками |
| Допсоглашения на правки сверх договора: Δ цена, Δ срок | `change_proposed`, `change_signed` | нужна ли реальная подпись или хватит фиксации согласия |
| Вопросы заказчика и очередь ответов у менеджера | `question`, `answer` | отдельный экран или блок на странице проекта |
| Недельный отчёт фоновой задачей | `report_sent` | канал доставки: письмо, SMS, только в кабинете |
| ИИ: черновики ответов, классификация изображений, генерация текста записи | — | нужен корпус данных из живого использования, раньше не браться |

Каждый вопрос в правой колонке способен изменить объём работы вдвое.
Не начинать пункт, пока на него нет ответа.

## Дизайн (задачи 7–8)

Светлый бумажный фон, тонкие линии, акцент — чертёжный синий `#1B3A73`.
Шрифты: Archivo для интерфейса, IBM Plex Mono для дат и чисел.
Индикатор прогресса — масштабная линейка с чертежа: 7 делений в ряд,
пройденные залиты, текущее приподнято и подписано номером этапа.
Тон текстов спокойный, без восклицаний и обращений.
Пустые состояния говорят о работе над проектом, а не о системе.
